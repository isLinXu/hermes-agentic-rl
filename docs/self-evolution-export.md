# Self-Evolution Export

`session-eval-export` turns Hermes session traces into a self-evolution dataset
with the `task_input` / `expected_behavior` shape used by downstream Hermes
agent improvement loops. The export is intentionally narrow: it preserves the
user task, the assistant behavior to imitate or evaluate, reward metadata, and
split provenance, while leaving policy training and skill packaging to separate
stages.

## When To Use It

Use `session-eval-export` after you have collected or replayed Hermes sessions
and want a stable dataset for:

- held-out behavior checks before promoting a checkpoint or worker;
- self-evolution examples grouped by optimization direction;
- later `skill-export` or manual review of high-value agent behaviors;
- training/evaluating BC, DPO, or reward-model workers outside the online loop.

For a complete online flow, `online-self-evolve` runs `online-cycle`, optional
Skill candidate export, and optional eval gates. For directional batch runs,
`self-evolution-batch` calls `session-replay`, `session-train-worker`, and
`session-eval-export` once per direction.

## Inputs

Supported sources:

- Session JSONL from `session-sidecar`
- Trajectory JSON from `rollout`
- Session bundles with `messages` or `metadata.messages`
- Replay records generated by `session-replay`

Typical session records contain a `session_id`, `task_id`, and a chronological
`messages` list. The exporter extracts assistant turns, nearby user/tool
feedback, reward summaries, capability axes, and replay mining metadata when
available.

## Configuration

Minimal config:

```yaml
input_path: outputs/hermes_online_cycle/sessions.jsonl
output_path: outputs/hermes_self_evolution_dataset
source: hermes-session
train_ratio: 0.7
val_ratio: 0.2
min_reward: 0.0
```

Common quality gates are usually applied one stage earlier in `session-replay`
or `session-train-worker`:

```yaml
data_quality:
  min_prompt_tokens: 2
  min_response_tokens: 4
  min_reward: 0.0
  max_abs_reward: 5.0
  min_unique_response_tokens: 2
  max_response_token_repetition: 0.85
  require_metadata_keys: [session_id]
  dedupe_within_scan: true
```

These gates reject malformed replay rows, too-short examples, extreme rewards,
low-diversity responses, repetitive responses, duplicate prompt/response/reward
triples, and rows missing required provenance metadata.

## Outputs

The output directory contains:

- `train.jsonl`: examples used for fitting workers or generating candidates.
- `val.jsonl`: examples for tuning thresholds and checking overfit.
- `holdout.jsonl`: examples reserved for final promotion checks.
- `manifest.json`: split counts, source paths, ratio settings, reward filters,
  and export metadata.

Each JSONL row includes:

- `task_input`: the user-visible task or prompt context;
- `expected_behavior`: the assistant action or response to preserve;
- `reward`: scalar reward used for filtering and ranking;
- `metadata`: session ids, task ids, source turn data, reward components,
  replay mining axes, and recommended downstream uses when present.

## Example Commands

Export from a standalone config:

```bash
python -m hermes_agentic_rl.cli.main session-eval-export \
  --config configs/session_eval_export_hermes.yaml
```

Run directional batch self-evolution:

```bash
python -m hermes_agentic_rl.cli.main self-evolution-batch \
  --config configs/self_evolution_batch.yaml
```

Run the online loop with export enabled:

```bash
python -m hermes_agentic_rl.cli.main online-self-evolve \
  --config configs/online_self_evolve.yaml \
  --once --limit 4
```

## What Gets Trained

The export itself does not update weights. It produces supervised/evaluation
data that later stages can use to train or validate:

- Tiny or HF-backed policy weights through GRPO/PPO;
- a PPO value head when value training is enabled;
- LoRA adapter parameters attached to an HF policy;
- reward-model heads for RM training;
- BC/DPO worker weights in the online replay loop.

If Hermes is driven by a remote OpenAI-compatible model, this project can still
collect traces, score behavior, train local workers/reward models, and export
self-evolution data. It does not mutate remote model weights unless that
provider exposes a separate training path.

## Reading Quality Reports

When a replay stage writes `quality_report_path`, inspect it before training:

- `input_rejections`: invalid JSONL or partial lines.
- `session_rejections`: records that could not be converted to session turns.
- `replay_invalid`: malformed token/reward records.
- `quality_filtered`: records rejected by configured data quality gates.
- `replay_mining`: capability axes, recommended uses, and Skill candidate
  counts.

Treat a high `quality_filtered` count as a data signal, not just a failure. It
often means the collection run produced weak feedback, repetitive outputs, or
insufficient provenance for later self-evolution.
